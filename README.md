# DNS Profile Manager

Текущая версия: **1.2.0**. История изменений — [CHANGELOG.md](CHANGELOG.md). Номер релиза хранится в [VERSION](VERSION); CLI и GUI используют одну версию по схеме `MAJOR.MINOR.PATCH`.

Менеджер DNS для Linux Mint / NetworkManager / systemd-resolved: CLI, терминальное меню и GTK-интерфейс используют общую конфигурацию и один механизм переключения.

## Установка и удаление

Поддерживаемая система — Linux Mint 22.x / Ubuntu 24.04 с действующим NetworkManager. Сначала подключите машину к сети средствами системы. Запускайте установщик обычным пользователем: для системной части он сам вызовет `sudo`.

```bash
./install --dry-run                   # показать подключения, пути и недостающие пакеты
./install --install-dependencies      # чистая машина: установить также недостающие пакеты
source ~/.bash_aliases
```

Если зависимости уже установлены, достаточно `./install`. Установка не перезапускает NetworkManager и не выполняет connection down/up. Начальный режим на чистой машине — DNS от DHCP. Меняются только DNS-поля физических подключений; VPN исключены. Создаются CLI-ссылки, один блок подключения Bash и ярлык GUI. Новый терминал получает команды из проекта, включая `~/.local/bin` в PATH.

Для **нынешней ручной установки** с `90-dns-route-refresh` используйте:

```bash
./install --dry-run --adopt-existing
./install --adopt-existing
source ~/.bash_aliases
```

Этот режим сохраняет работающий профиль MagicDNS/Dagami и архивирует прежний Dispatcher. Его содержимое не исполняется из пользовательского каталога. Без флага установщик откажется заменять существующую ручную интеграцию. Повторная установка сохраняет исходную резервную копию; для смены набора управляемых подключений сначала выполните удаление.

По умолчанию управляются все сохранённые Ethernet/Wi-Fi профили. Можно ограничить набор UUID (параметр повторяется):

```bash
nmcli -f UUID,TYPE,NAME connection show
./install --connection UUID_ETHERNET --connection UUID_WIFI
```

Параметры и отчёты находятся **внутри проекта**:

- `.local/config/providers.json` — общий конфиг провайдеров CLI и GUI.
- `.local/config/network.json` — UUID физических подключений и путь управляемого DNS-профиля этой машины.
- `.local/config/commands.bash` — генерируемые CLI-команды.
- `.local/cache/` — отчёты, результаты проверок и блокировка операций.
- `.local/installation.json` — состояние установки и привязка к машине.
- `.local/backups/` — исходные файлы пользователя и копии системного журнала для восстановления.
- `.local/dns-ai/` — загружаемые через `dns-ai-update` скрипты; автоматически они не запускаются.

Прежние `~/.config/dns-manager` и `~/.cache/dns-manager` переносятся в проект и заменяются ссылками совместимости. Различающиеся данные автоматически не перезаписываются. `.local/` исключён из Git: для переноса собственных настроек копируйте **весь каталог проекта, включая скрытую `.local`**. На новой машине снова запустите `./install`: UUID и интеграция создадутся заново, конфиг провайдеров сохранится. На исходной машине перед переносом/переименованием каталога выполните `./uninstall`.

В систему устанавливаются root-owned копия Dispatcher, JSON с разрешёнными UUID, настройка NetworkManager и DNS-файл resolved. Dispatcher не загружает код из проекта или домашнего каталога. Доверенный журнал исходных системных настроек хранится в `/var/lib/dns-profile-manager/installation.json`; его копия сохраняется в проекте. Это необходимо, чтобы системное восстановление не доверяло изменяемой пользователем резервной копии.

```bash
./uninstall --dry-run
./uninstall
```

Удаление отключает все управляемые DNS-профили: удаляет глобальный DNS-файл, наш и перенесённый старый Dispatcher, перенесённые `dns-ai.conf` / `dagami.conf` / `magicdns.conf`, пользовательские ссылки, ярлык и блок Bash. На всех управляемых Ethernet/Wi-Fi профилях, включая неактивные, очищаются ручные IPv4/IPv6 DNS и разрешается получение DNS от DHCP. Активные подключения применяются через `device reapply`; неактивные не подключаются. Прежние ручные DNS и Dispatcher **не восстанавливаются**. **Каталог проекта, конфиги, отчёты и резервные копии остаются.** Штатный systemd-resolved остаётся включённым, а `resolv.conf` — подключённым к его stub: это системный механизм работы DNS от DHCP. Наш файл настройки NetworkManager удаляется. Общие системные пакеты не удаляются, NetworkManager продолжает работать. Загруженные функции остаются в памяти старых терминалов до их закрытия; переключение после удаления блокируется.

Если управляемый системный файл изменён другой программой, удаление останавливается, сохраняя журнал. Восстановление прежних настроек используется только для отката неудачной установки, отдельно от удаления. При сбое установки выполняется попытка такого отката; состояние и ошибка записываются в `.local/installation.json`. Если откат не завершился, устраните указанную причину и повторите `./uninstall`.

## Запуск

```bash
./dns-gui          # GTK-интерфейс
./dns-menu         # терминальное меню
./dnsctl --version # версия приложения
./dnsctl list      # список провайдеров и CLI-команд
./dnsctl current   # фактический DNS и основной маршрут
```

Приложение использует системный `/usr/bin/python3` с PyGObject / GTK 3 / Pango. Также нужны NetworkManager, systemd-resolved, curl, kdig; для терминального меню — dialog, для графического запроса пароля — zenity. Недостающие зависимости установщик устанавливает только при явном `--install-dependencies`.

Кнопка **«Статус DNS»** соответствует CLI-команде `dns-status`; **«Подробности сети»** — команде `dns-details`. Результат отображается в области отчёта.

## Общий конфиг

Рабочий файл после установки: `.local/config/providers.json` внутри проекта. `~/.config/dns-manager` служит ссылкой совместимости.

`providers.default.json` — начальный шаблон; после установки изменения вносятся в рабочий файл. В нём находятся IP-адреса, протокол, порт, TLS-имя, название, описание, сайт и CLI-команды каждого провайдера. Режимы: `dhcp`, `dot`, `plain`. Нативного применения DoH здесь нет: systemd-resolved используется с DoT либо обычным DNS.

В GUI выберите провайдера → **Настроить**, либо **Добавить провайдера**. Сохранение не переключает DNS. Для применения используется отдельная кнопка. Настройки DHCP-провайдера не содержат ручных адресов.

Пример нового провайдера:

```json
{
  "id": "example",
  "name": "Example DNS",
  "mode": "dot",
  "servers": ["203.0.113.10"],
  "tls_hostname": "dns.example.org",
  "port": 853,
  "command": "dns-example-on",
  "off_commands": ["dns-example-off"],
  "website": "https://example.org/",
  "description": "Пример структуры, адрес не является рабочим DNS"
}
```

При сохранении через GUI или CLI импорта автоматически обновляются `commands.bash` и команды в `~/.local/bin`. Новый провайдер появляется в обоих интерфейсах. CLI-команды читают параметры из JSON при каждом вызове.

```bash
./dnsctl config path
./dnsctl config show
./dnsctl config import /путь/к/providers.json
./dnsctl config sync-commands  # после ручного редактирования JSON
```

Имена ограничены пространством `dns-*` / `xbox-dns-*`; существующие посторонние команды не перезаписываются. Для обновления функций в уже открытом Bash выполните `source ~/.bash_aliases`. Новые исполняемые команды доступны через `~/.local/bin`, если он есть в PATH.

## CLI

Сохранены команды `dns-provider`, `dns-magic-on/off`, `dns-dagami-on/off`, `dns-ai-on/off`, `xbox-dns-on/off`, `dns-status`, `dns-details`. `dns-ai-update` остаётся отдельной командой скачивания установщика; применение DNS-AI его не запускает.

```bash
./dnsctl apply magic
./dnsctl apply dagami
./dnsctl apply provider
./dnsctl status
./dnsctl details
./dnsctl check ai
./dnsctl check --all
./dnsctl check --all --json
# Аналогично после подключения команд:
dns-check magic
dns-check --all
```

`apply` меняет DNS. **`check` не изменяет DNS и не требует sudo.** Код завершения `check`: 0 — все проверки успешны, 1 — есть частичные/неуспешные результаты, 2 — ошибка выполнения. В режиме JSON возвращается список подробных результатов.

## Проверка без переключения

Запросы отправляются непосредственно каждому IP из конфигурации. Для DoT проверяются цепочка сертификата, TLS-имя и SNI; незаметного перехода на незашифрованный DNS нет. В DHCP-режиме адреса читаются из DHCP активных известных подключений, даже когда системно выбран другой профиль.

В версии 1.1 проверяются **Claude, Gemini, ChatGPT, Perplexity, Google AI Studio, Antigravity** и контрольный **GitHub**. В GUI кнопка **«Проверить без переключения»** открывает отдельную панель: карточки сервисов, текущие этапы, сводные показатели и **«Проверить снова»**. Кнопка **«Результаты»** позволяет открыть свежий сохранённый отчёт без повторных запросов. В панели можно выбрать результат другого профиля; «Проверить все» последовательно проверяет весь список провайдеров.

Панель следует структуре [виджета MagicDNS](https://magicdns.ru/): карточки, прогресс, метрики и повторная проверка. После изучения его JavaScript обнаружены `no-cors` запросы, резервные домены других сервисов и расчёт отображаемого RTT с добавлением случайного числа. В нашем приложении выводятся наблюдаемые этапы сетевого запроса; доступность одного постороннего домена не подменяет проверку нужного сервиса.

Для каждого сервиса:

1. Запрашивается A-запись напрямую у каждого DNS-сервера профиля. Для DoT проверяется сертификат и TLS-имя.
2. HTTPS запрашивается через `curl --resolve` по первому IPv4 из каждого ответа сервера. Одинаковые пары домен/IP объединяются. Сохраняются исходное имя сайта, SNI и проверка сертификата. Прокси и пользовательский `.curlrc` не используются.
3. Измеряются TCP, TLS, время первого байта и полное время HTTPS; фиксируются HTTP-код, проверенные IP и причина ошибки. DNS-время включает весь DNS-запрос, в том числе установку DoT-соединения.
4. До пяти HTTPS-перенаправлений проверяются вручную: новый домен разрешается через тот же DNS-профиль. Переход на HTTP, IP вместо имени или нестандартный HTTPS-порт не выполняется. Системный DNS не служит запасным резолвером.

Тело ответа ограничено 256 КиБ. Срабатывание лимита после подтверждённого HTTPS-ответа не считается обрывом соединения. Cloudflare Challenge определяется по заголовку `cf-mitigated: challenge`, региональные сообщения — по ограниченному анализу JSON-ошибки или заголовка страницы. Отсутствие этих признаков не доказывает отсутствие любых CAPTCHA или региональных ограничений.

- **Зелёная ✓ у профиля:** все DNS-серверы дали пригодные ответы для целевых доменов и все проверенные HTTPS-цепочки завершились ответами 2xx без обнаруженного ограничения.
- **Жёлтая ⚠ у профиля:** часть DNS/HTTPS-проверок не пройдена; в том числе HTTP 403/429, Challenge, ошибка TLS или неполное перенаправление при работающем DNS.
- **Красная ✕ у профиля:** ни один сервер не вернул пригодный DNS-ответ для тестовых доменов.
- **Серая ○:** проверка отсутствует, устарела или не может быть выполнена.

Карточка отдельного сервиса красная и при полной недоступности TCP/TLS/HTTPS этого сервиса; состояние всего профиля при работающем DNS остаётся жёлтым. Сводка ИИ учитывает только сервисы с ролью `ai`; GitHub имеет роль `control`. Медианы вычисляются из измеренных значений. TCP/TLS-время цепочки — сумма соответствующих этапов её переходов; это не RTT. Сетевая доступность без входа в аккаунт не подтверждает генерацию ответов, работу API или отсутствие CAPTCHA после авторизации.

Список целей хранится в том же `providers.json`:

```json
"test_services": [
  {"id": "claude", "name": "Claude", "host": "claude.ai", "role": "ai"},
  {"id": "github", "name": "GitHub", "host": "github.com", "role": "control"}
]
```

Поддерживается от 1 до 20 уникальных доменов. Старый `test_domains` продолжает читаться. Чтобы добавить базовый расширенный набор в конфиг старой версии с сохранением настроек провайдеров и пользовательских целей:

```bash
./dnsctl config upgrade-checks
```

Кэш `~/.cache/dns-manager/health.json` устаревает через 15 минут, при смене сети, изменении DHCP DNS, параметров профиля, списка целей, таймаутов или схемы диагностики. Если сеть изменилась во время проверки, результаты помечаются как требующие повтора. Проверка не переключает интерфейсы для сравнения разных сетей.

## Согласование с установленными Bash-скриптами

DNS-команды подключаются из проекта одной строкой в `~/.bash_aliases`:

```bash
[[ ! -r '/путь/к/dns-profile-manager/shell/dns.bash' ]] || source '/путь/к/dns-profile-manager/shell/dns.bash'
```

- `shell/dns.bash` — точка подключения CLI-команд и отдельной `dns-ai-update`.
- `shell/network.bash` — общая сетевая логика CLI и GUI.
- `.local/config/network.json` — физические подключения и системные пути; прежний `network.bash` поддерживается до перехода на новый установщик.
- `~/.config/dns-manager/providers.json` — адреса и параметры провайдеров, цели диагностики.
- `~/.config/dns-manager/commands.bash` — автоматически созданные маршруты CLI-команд к провайдерам из JSON; их загружает `shell/dns.bash`.

Для переноса установленной DNS-конфигурации:

```bash
/usr/bin/python3 integrate.py
source ~/.bash_aliases
```

Прежняя команда `integrate.py` предназначена только для установок до 1.2.0; после `./install` используйте новый установщик. Она переносит известный DNS-раздел из `~/.bash_aliases`, сохраняет резервную копию в `~/.config/dns-manager/backups/` и заменяет только этот раздел защищённым `source`. Команды до и после него, включая VS Code / Xray, сохраняются. Неизвестные строки внутри старого DNS-раздела или конфликт с существующим `network.bash` останавливают автоматический перенос. Повторный запуск с актуальным подключением не переписывает общий файл.

CLI и GUI **не загружают `~/.bash_aliases`**: они напрямую используют `shell/network.bash` и локальные настройки. Поэтому посторонние команды из общего файла не выполняются при диагностике или переключении. `DNS_ALIASES_FILE` переопределяет файл только для установщика; `DNS_MANAGER_NETWORK_CONFIG` позволяет указать другой локальный файл сетевых параметров.

При переключении меняются только активные известные физические подключения, используется `nmcli device reapply`. Глобальный профиль новой установки — `/etc/systemd/resolved.conf.d/90-dns-profile-manager.conf`; при переносе сохраняется существующий `90-alex-dns-profile.conf`. DHCP возвращается удалением управляемого профиля. При полном удалении ручные DNS очищаются также у неактивных управляемых подключений. Старый Dispatcher и старые профили остаются только в резервных копиях проекта.

Операции CLI/GUI блокируются общим пользовательским lock. После авторизации сетевой модуль получает lock существующего Dispatcher `/run/lock/nm-dns-primary-route.lock`; конфиг resolved заменяется атомарно. Метрики, VPN, прокси-переменные и неактивные подключения не изменяются. Сам системный Dispatcher при миграции не редактируется. GUI работает от обычного пользователя; sudo применяется только для привилегированных сетевых операций.

## Проверки разработки

```bash
/usr/bin/python3 -m unittest discover -s tests -v
```

Тесты проверяют конфигурацию, создание команд, блокировки, актуальность статусов, DNS/TLS/HTTPS с подменённым транспортом, перенаправления, Challenge/403, этапы измерений и применение к Ethernet/Wi-Fi с подменённым nmcli. Новые тесты установщика используют временную файловую систему и подменённые системные команды: проверяют откат, удаление и сохранение чужих файлов. Они не переключают системный DNS. По договорённости тесты запускает пользователь.

Ручная проверка интерфейса:

```bash
./dns-gui
```

Выберите MagicDNS → «Проверить без переключения». Ожидаются отдельное окно, семь карточек, текущие этапы, итоговые HTTP-коды и измеренные задержки. «Проверить снова» повторяет выбранный профиль. Закрытие панели или Esc скрывает её, повторное нажатие «Результаты» возвращает окно. При выполнении проверки профиль можно просматривать в панели, но применение другого профиля из основного окна заблокировано до завершения операции.

Сетевая диагностика через CLI, также без переключения:

```bash
./dnsctl check magic
./dnsctl check magic --json > /tmp/dns-profile-report.json
```

HTTP 403/429 или таймаут могут быть реальным результатом из вашей сети: это не означает ошибку самих unit-тестов. Код 1 у `dnsctl check` означает ограничения/неуспешные сетевые проверки; unit-тесты при успешном выполнении заканчиваются строкой `OK`.

Проверку настоящей установки и удаления на чистой машине проводите в отдельной VM с Mint 22.x: `./install --dry-run`, `./install --install-dependencies`, запуск CLI/GUI, затем `./uninstall`. После удаления проверьте доступность сети, получение DNS от DHCP, отсутствие Dispatcher/старых DNS-профилей и команд в новом терминале, а также сохранность `.local/config/providers.json`; повторная установка должна использовать этот же конфиг.
